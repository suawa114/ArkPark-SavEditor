研究日期：2026-10-16。只读取已安装游戏资源与玩家存档，未启动游戏、未修改游戏资源、未写入玩家存档。测试仅在 Python 内存副本中进行。

## 结论

| 问题 | 当前结论 | 证据性质 |
| --- | --- | --- |
| 正常游戏生成多少项附加技能？ | 已核实的发射器通用随机生成函数固定抽取 **3 个不同枚举**。 | 游戏蓝图字节码静态证据 |
| 存档结构是否最多只能存 3 项？ | **不是。** 它是动态枚举数组，没有固定 3 格结构。4、21、22 项的内存序列化、重新解析和还原检查均通过。 | 结构分析与本地序列化实验；不是游戏实测 |
| 超过 3 项是否会被前三项截断？ | 已核实的核心触发路径使用完整数组的 `Array_Contains`，没有取前三项；但不能由此保证所有加载、显示和联机路径都无限兼容。 | 核心触发路径静态证据 |
| 一共有多少种已知合法技能？ | **21 种**：7 种元素各 3 级。21 是不同合法技能的数量，不是数组条目硬上限。 | 已发布枚举与触发分支 |
| 重复添加相同技能能否按数量叠加？ | 已核实触发路径是布尔存在判断，重复相同枚举不会在这条路径中因条目增加而重复触发；同元素有高级优先的回退分支。 | 控制流分析 |
| 修改器当前允许多少项？ | v0.4.0 按用户要求移除原 `SKILL_LIMIT = 3`；允许添加、编辑超过 3 项的已知技能列表，保留顺序和重复项。格式与资源保护仍有效。 | 当前源代码 |
| 能否立即认定修改上限为 21？ | **不能。** 文件结构允许，但超过 3 项的游戏内重载、实际效果、再次保存均未实测。 | 明确的验证边界 |

## 正常随机生成：固定抽 3 个

资源包：`/Game/InfimaGames/LowPolyShooterPack/Core/Weapons/BP_LPSP_WEP`。

`随机等级` 函数为 export 246：

1. 字节码位置 5 创建枚举值 0–20，共 21 项。
2. 位置 58 存为 `临时核心库`，位置 85 调用 `Array_Shuffle`。
3. 中间按等级随机分配数值增益；这些数值的 Clamp 不是技能数量上限。
4. 位置 494 的 `EX_SetArray` 明确只读取打乱数组的索引 **0、1、2**。
5. 位置 550 赋给 `抽到核心`，位置 604 赋给输出参数 `核心`。
6. 通用事件图位置 58660 调用 `随机等级`，位置 58728 将其结果赋给 `S_发射器数据.携带的核心`。

因此这条正常生成路径产生 3 个不同枚举，同元素不同等级属于不同枚举，可能同时出现。不能把“3 个不同枚举”误解为“3 种不同元素”。当前样本的雷电2、风暴3、雷电1与此相容。

对应证据：`capacity-weapon-246.json`、`capacity-generation-compact.json`、`capacity-weapon-51.json`。同时检查了已定位的发射器升级/改造 UI、核心拾取相关包；未在这些检查范围中建立独立“安装第 4 技能”的正常游戏操作路径。此有限检索不能排除其他特殊模式或后续版本存在另一生成器。

## 运行时不是按前三项读取

`激活核心`（export 227）进入通用事件图位置 14936。

- 位置 14975 只检查 `携带的核心` 的索引 0 是否有效，即数组非空。
- 后续分别以 `Array_Contains` 检查完整数组中是否含有各枚举。
- 例如火焰3在 15252 检查；不存在时跳到 20481，再于 20501 检查火焰2；仍不存在则在 21588 检查火焰1。低级不是与高级无条件一起执行的独立次数循环。
- 其余冰霜、雷电、腐蚀、风暴、古怪、工程也有对应的 3→2→1 检查链，共覆盖 21 种枚举。
- 同一相同枚举重复 N 次仍只改变“是否包含”的布尔值，不会自动变成 N 次触发。

这说明第 4 项起在已核实触发路径中仍能参与查找，不存在“核心触发统一只读前三项”的限制。技能效果还有概率、目标类型和其他运行时条件，不能把“查到了枚举”等同于每次命中都会生效。

对应证据：`capacity-weapon-227.json`、`capacity-weapon-51.json`、`capacity-runtime-compact.json`、`capacity-runtime-references.json`。

## 存档容量与只读实验

技能字段是 `S_当前使用的的发射器[i].携带的核心_44_42378C144D5A202F5425779A948C058A`，资源结构为 `ArrayProperty → ByteProperty → E_发射器元素核心`。GVAS 存档里每个元素使用完整枚举 FString 名称保存，数量为带符号 32 位计数，不是一个容量为 3 的静态槽表，也不是因为 ByteProperty 就只能放 255 项。

当前底层解析器/数组重建器的人为防御上限为 200000 项、属性长度不能超过带符号 32 位可表示范围；这些只是实现与格式约束，不是游戏允许值。重复 22 项能编码，也不意味着有第 22 种有效技能。

## 未解决项与覆盖限制

- 未验证超过 3 项在游戏中加载、UI展示、触发效果与重存后是否保留，因此可靠可用上限尚不能从静态证据给出。
- 没有声称全游戏所有模式、子类和联机路径都完成穷尽分析。当前强证据覆盖通用发射器随机生成与核心激活路径。
- CUE4Parse 在通用武器默认对象的 `HitResult` 映射、关联玩家类部分属性上报告解析限制；本报告依据已独立导出的函数字节码与明确结构，未使用失败的默认对象数据推断上限。
- 现有已通过游戏测试的火力等数值修改，与新增技能尤其超过 3 项的效果验证是不同事项。
